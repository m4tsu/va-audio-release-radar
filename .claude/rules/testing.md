# テストの規則

## 何をテストするか

書く前に、そのテストが落ちたときに壊れたのは何かを考える。

| 落ちたときに壊れたもの | 書くか | 例 |
|---|---|---|
| このアプリの判断 | 書く | 出す文言、絞り込み、並び、保存、操作の結果、テーマの切り替えで `html` の `.dark` が変わること、ストアごとの成果計測画像を出すか出さないか |
| フレームワーク・ライブラリ・ブラウザ | 書かない | React が props を DOM に出すこと、Tailwind や `tailwind-merge` のクラスの扱い、Radix の既定の開閉 |

理由: 書いたものが書いたとおりにあることを確かめるテストは、書き換えるたびに一緒に書き換えるだけで、
このアプリの判断が壊れたことを知らせない。落ちても直す先がこのアプリのコードに無い。

## 見た目はテストしない

次はどれも「書いた CSS がそのまま効くか」を見ているだけなので書かない。

- CSS の定義: `src/index.css` を読んでトークンの値・色の違い・コントラスト比を比べる
- class の文字列: 要素やクラス定数がどの class・どのトークンを指すかを比べる
- 計算済みスタイル: `getComputedStyle`、`toHaveStyle`
- E2E での見た目: `toHaveCSS`、`toHaveClass`、スクリーンショットで色を確かめる

色やトークンを決めたときの判断はテストではなく、定義の隣のコメントに理由として書く。

`npm run check` の `check:layers` (`scripts/check-app-layers.mjs`) が、`src/` と `e2e/` のテストで
CSS ファイルの読み込み、`getComputedStyle`、`toHaveStyle` / `toHaveCSS` / `toHaveClass`、
`getAttribute("class")` を落とす。これらに当たらない書き方でも、上の判定で書かないものは書かない。
