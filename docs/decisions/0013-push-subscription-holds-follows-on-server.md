# 通知を購読したブラウザのフォローはサーバーが持つ

読者: フォローの保存先、通知の宛先、Worker から外へ出る通信を変えようとする人
更新: ログインを入れてフォローの正をサーバーに移す判断をしたら superseded にして新しい決定を書く
削除: superseded になっても消さない

状態: accepted (2026-09-22)。[`0005`](./0005-follow-state-in-browser.md) を置き換える

## 状況

フォローはブラウザの IndexedDB にだけあり、サーバーは知らなかった ([`0005`](./0005-follow-state-in-browser.md))。
通知には宛先と「誰の新作を知らせるか」が要る。ログインを入れると閲覧の入口が狭くなり、
年に数本しか鳴らない通知のためにアカウントを作る人は少ない。

## 決定

通知は Web Push で、アカウント無しで購読できるようにする。購読したブラウザは、push service が払い出した
宛先とフォロー中の声優をサーバーに送り、フォローが変わるたびに送り直す。サーバーはその写しを持ち、
週 1 回の cron で新作のある購読にだけ 1 通送る。購読していないブラウザのフォローは従来どおりブラウザにだけある。
宛先は利用者の識別に使わない。

## 帰結

- サーバーがフォローを持つのは購読中のブラウザの分だけで、正はブラウザ側にある。SSR でフォローは読めないまま
- Worker から外へ出る通信に push service が加わる (お問い合わせの bot 対策に続く 2 つ目)
- 宛先はブラウザ単位なので、端末をまたいで届かず、ブラウザのデータを消すと購読も消える。
  失効した宛先は送信で分かり、その時点で消す
- プライバシーポリシーに、購読中にサーバーへ送るものと push service への通信を書く

## 採らなかった案

- ログインを前提にしてメールで送る。宛先の確かさは高いが、登録の手間と送信基盤の契約が先に要る。
  併存は可能で、この決定はその順序を「Web Push が先」と定めるもの
- RSS。読み手側の道具が要り、主手段にはしない ([`product.md`](../product.md) の「通知」)
