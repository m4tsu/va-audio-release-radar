# 台帳は DB で、途中のファイルを持たない

読者: 対象声優やアニメの置き場、取得範囲と対象集合の関係を変えようとする人
更新: 台帳の置き場か、取得範囲の扱いを変えたら superseded にして新しい決定を書く
削除: superseded になっても消さない

状態: accepted (2026-09-22)。[`0009`](./0009-actor-list-append-only.md) を実装に落とし、その帰結を置き換える

## 状況

対象声優は AniList から機械的に決める ([`0001`](./0001-target-actors-from-anilist.md))。
リストは追加だけを行うと決めていた ([`0009`](./0009-actor-list-append-only.md)) が、生成は
毎回ゼロから作り直す形だった。取得結果に居ない人は出力から落ち、落ちないよう欄ごとに
「消えたら止める」検査と、作り直さずに書き戻す別のスクリプトを足していた。

作り直すたびに人が落ちる理由は、当初「シーズンの窓から外れたから」と説明していた。
[`anilist-cast-instability-2026-09-22.md`](../research/anilist-cast-instability-2026-09-22.md) の測定で、
実際の原因は 1 作品あたりの出演者を 25 人で切っていたことだと分かった。同じ役の中の順序は
取得ごとに変わるので、窓を動かさなくても毎回 100 人規模が入れ替わる。

## 決定

- **台帳は DB の行。** 声優・アニメ・出演は取得したその場で取り込み API に送る。
  git に入る生成物も、取得結果を溜める中間ファイルも、台帳としては持たない
- **取得範囲は対象集合を狭めない。** シーズンの窓と 1 シーズンあたりの作品数は取りに行く範囲を
  絞る条件であって、対象から外す条件ではない。範囲から外れた声優・作品・出演も行として残る
- **1 作品あたりの出演者は上限で切らず、ページを送って全員取る**
- **声優のデータを 3 種類に分ける。** 同一性 (staff id・ID・slug・初めて見た日時) は作られた後に
  変えない。供給元の写しは取り込みが今回言った項目だけを上書きする。付加情報 (かな、表示用
  ローマ字、公開状態) は 声優 × 属性 × 出どころ で 1 行を持ち、書き手は自分の出どころの行しか触らない

## 帰結

- 声優が取り込みで消える経路が無くなる。欄ごとの「消えたら止める」検査と、作り直さずに
  書き戻すスクリプトが要らなくなる
- 生成に中間ファイルが要らないので、それを持たない場所 (CI、別の作業ツリー) でも同じ結果になる
- 声優の ID と slug を決めるのは Worker になる。slug の衝突は今ある全員と突き合わせないと解けず、
  それを知っているのは DB だけ。衝突した後から来た人の slug には staff id を付ける
- 声優起点の走行は誰を調べるかを取り込み API から引く。リストのファイルを配らない
- 同じ日本語表記の別人も台帳に入る。ストアのクレジット表記から誰かを断定できないのは変わらないが、
  それは照合が「複数に当たったら unmatched」で断っている ([`0002`](./0002-actor-first-crawling.md) の名寄せ)
- 1 作品あたりの往復が増える。上限に当たる作品だけページを送るので、増えるのは測定時点で
  1,175 作品中 309 作品ぶん

## 採らなかった案

- **生成物を「前回の出力に足す台帳」にする。** ファイルが台帳なら、取得結果・生成物・DB の 3 つの
  状態を合わせる仕事が残り、合わせ損ねたときに声優が消える経路も残る
- **1 作品あたりの取得人数の上限を上げる。** 上げても上限は残り、同じ役の中の順序は不定のまま。
  実際 `perPage` は 25 に丸められるので上げられない
- **消える人を数えて止める。** 止まった後に人が無視して進めるか、書き戻す仕組みを足すかの
  二択になる。これまでがその形だった
- **窓から外れた声優に印を付けて区別する。** その値を読む場所が無い
