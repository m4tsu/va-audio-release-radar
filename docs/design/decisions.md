## 1. カテゴリ判定をジャンルだけでなくタイトルからも行う

**決定**: `categorize()` の判定材料をジャンル + タイトルに広げ、「ボイスドラマ」「ドラマCD」
「オーディオドラマ」を含むものを `audio_drama` にする。どれにも当たらなければ `asmr` に落とす。

**日付**: 2026-09-18 (夜間実装 T6)

**根拠**: `product.json` 200 件を集計したところ、**DLsite のジャンルに「ドラマ」
「シチュエーション」という語が 1 件も無かった**。旧規則 (ジャンルだけを見る) では
200 件すべてが `asmr` になる。ドラマ作品を見分けられるのはタイトルだけだった。

**覆したもの**: ジャンルだけを見る旧規則。実データで全件が同じカテゴリに落ちたため。

**詳細**: ジャンルの分布、19 件の内訳、既知の取りこぼしは
[`../stores/dlsite.md`](../stores/dlsite.md) §6。

## 2. 対象声優を AniList 交差で機械的に決める

**決定**: 対象声優 = AniList にアニメ出演記録がある日本語声優。人が名前を挙げるのをやめ、
AniList から自動生成する。手書きシード 35 人は暫定扱いにする。

**日付**: 2026-09-18 (日中ブレスト)

**根拠**: 製品のコンセプトは「アニメ声優との接続」であり、DLsite にしか居ない同人 ASMR の
声優はフォロー対象ではない。直近 12 シーズンから **2,569 人** (2026-09-18 実測) が機械的に得られ、
交差した 57 人の 90 日作品は週 5.8 件で、暫定シード 35 人 (週 1.0 件) の 5.8 倍だった。

**覆したもの**: 企画書の「人が選んだ声優リストから始める」。
当初は「需要側 (AniList) と供給側 (DLsite sitemap) の交差」を対象の定義にしていたが、
§7 でストア側からの発見が不要になり、**AniList 単独が対象の定義**になった。

**付随して決めたこと** (T13 / T14): slug はワープロ式表記をそのまま使う。1 語の名義も残す。
slug が衝突したら生成を失敗させ、人が overrides で解決する。

**詳細**: 生成規則は [`../stores/anilist.md`](../stores/anilist.md) §6、実測は
[`../research/discovery-spike-2026-09-18.md`](../research/discovery-spike-2026-09-18.md)。

## 3. 新着を発売日基準にし、フィードを 3 段にする

**決定**: NEW バッジと「今週の新着」は `release_date` が 7 日以内。並びは発売日の降順。
フィードは 今後の発売 / 30 日以内の新作 / それ以前 (折りたたみ、90 日) の 3 段。
未読は最後にフィードを見た日時をブラウザ (Dexie) に持って判定する。

**日付**: 2026-09-18 (日中ブレスト)

**根拠**: `first_seen_at` だけで新着を判定すると、初回クロールと声優追加のたびに
全作品が新着になる。3 段にするのは上 2 段が空でも画面が空にならないようにするため。
発売日の無い作品だけ、初回クロール以降に見つかったものを新着扱いにする。

**覆したもの**: 企画書の「発見日基準」。

**詳細**: [`architecture.md`](./architecture.md) §7。

## 4. 90 日制限は実装上の制約ではなかった

**決定**: 声優ページは back catalog (全期間) を主内容にする。取得の上限を気にする必要はない。

**日付**: 2026-09-18 (A4 調査)

**根拠**: **`per_page` は無視されるだけ**で、robots も 1 ページ目を明示的に許可していた。
総件数は `pager.count` から必ず取れる。上田麗奈の全期間 27 件は 1 ページ目で 100% 網羅できており、
30 件を超えうるのは 245 名義中 4 名義 (2%)、いずれも対象外の同人 ASMR 専業だった。

**覆したもの**: 企画書 §5 の「直近 90 日」と、それを技術的制約だと思っていた認識。
あわせて **「`per_page/100` を付けると 0 件になる」という記録**を覆した。再現しなかった。
「全期間を取る手段をどうするか」という課題そのものがほぼ存在しなかった。

**残した対応**: `pager.count` を `crawl_runs` に記録し、実取得件数が下回った場合だけ
`order/release` (古い順) を足して 60 件まで補完する。

**詳細**: robots の引用と `per_page` の挙動は [`../stores/dlsite.md`](../stores/dlsite.md) §1 / §6。

## 5. 製品の性質を「めったに鳴らない通知」と再定義した

**決定**: 製品は「頻繁に見に来るフィード」ではなく「めったに鳴らないが、鳴ったら確実に届く通知」。
声優ページの主内容は back catalog で、その上に新着を知らせる層を載せる。
通知は新作が出た週だけ 1 通、空の週は送らない。

**日付**: 2026-09-18 (日中ブレスト)

**根拠**: アニメ本業の声優の音声作品は年に数本。実データ (35 人、直近 90 日) は
DLsite 17 件 / Audible 4 件 = **週 1.6 件**。この頻度で毎日見に来るサービスは成立しない。

**覆したもの**: kill criteria の「フィードが薄い」。指標も入れ替えた。

| 外した指標 | 代わりに見る指標 |
|---|---|
| feed views | 声優ページ → フォロー (通知登録) の転換率 |
| フィード密度 (新作数 / 週) | 通知 → ストア送客のクリック率 |

GO / NO-GO で見る厚みも「音声作品が 1 本以上ある対象声優の人数」と
「1 人あたりの作品総数」を主指標にし、直近 90 日の新作数は通知頻度の参考値に格下げした。

## 6. 差別化の柱を出演形態に置いた

**決定**: 出演形態 (単独 / 少人数 / 全編朗読 / 大人数) を差別化の軸にする。
共演バッジは低優先、商業イベント (セール / 予約 / 無料) はスキップ。

**日付**: 2026-09-18 (外部レビューの 3 案を実データ 90 日 428 作品で検証)

**根拠**: 出演形態は `voice_by` の配列長で判定でき実装コストがほぼゼロで、実データでも分かれる
(DLsite は 61% が単独)。共演は 75 件中 16 件あるが中身は「同じ企画への複数出演」で、
集合積でいつでも実装できる。商業イベントはセール中が 41% で常態であり、通知の材料にならない。

**覆したもの**: 外部レビューはフィードを濃くする方向を提案していたが、本プロジェクトは実測から
「フィードは薄いのが前提、back catalog が主内容」と結論している (§5)。**実測値のある側を採った。**
ただし判断規則「この機能はフォロー情報があるから成立するか」は採用した。

**あわせて決めたこと**: 差別化の軸は「フォローした声優の新着を、ストアを問わず取りこぼさず
知らせる」。ストア横断はその手段の 1 つで、Audible は中核ではなく 2 号ストア。

**詳細**: [`../research/codex-differentiation-spec.md`](../research/codex-differentiation-spec.md)。
セールの実測値は [`../stores/dlsite.md`](../stores/dlsite.md) §6。

## 7. DLsite は声優起点。全件取得はしない

**決定**: DLsite は声優名の完全一致検索の 1 ページ目だけを引く。sitemap による全件発見はしない。
`product.json` を含む全パスを robots.txt の `Crawl-delay` に揃える。

**日付**: 2026-09-18 (日中ブレスト。間隔の修正は T12)

**根拠**: `Crawl-delay` を守ったときのコスト比較で、声優起点は sitemap 全件より **27 倍速い**
(時間の内訳は [`../stores/dlsite.md`](../stores/dlsite.md) §2)。
sitemap による全件発見は「AniList に居ない声優の発見」にしか要らず、それは対象外 (§2)。

**覆したもの**: 「sitemap で全年齢音声作品を全件発見して声優を洗い出す」という当初の交差の取り方。
あわせて **「`product.json` だけ間隔を短くしてよい」という誤り**を覆した。
`Crawl-delay` は `User-agent: *` グループにありパスの限定が無いので、API にも及ぶ。

**詳細**: [`../stores/dlsite.md`](../stores/dlsite.md) §1 / §2。

## 9. 全年齢のみという制限を外し、全年齢 + BL にした

**決定**: 対象は **全年齢 + BL (全年齢 BL)**。R18 は載せない。**日付**: 2026-09-18 (A6 調査)

**根拠**: R18 を載せても対象声優の作品は **1 件も増えない** (DLsite maniax は代表 10 名で home と
同一、ポケドラのオトナ向けは AniList 対象声優との一致 0 名)。一方 Amazon アソシエイトは
「露骨な性的描写がある場合」を参加申請をお断りするサイト例に挙げており、R18 を載せると
Audible の送客経路を失うリスクだけが残る。
逆に **BL は必須**で、外すと男性声優の対象作品を大きく失う (斉藤壮馬は 143 件中 98 件が BL)。

**覆したもの**: 企画書 §26 の「全年齢のみ」。および設計書の
「導入しないもの: …成人向け作品」という一行 (BL が落ちるため)。

**設計への波及**: `AudioWork.adult: boolean` では BL と一般を区別できないので、年齢区分を真偽値
ではなく列挙 (`general` / `r18` / `unknown`) に変えた。**BL は年齢区分に入れず**、ストア固有の
区分を `StoreListing.storeSection` に持たせた。4 値案 (`general` / `bl` / `r18` / `r18_bl`) は採らない。

**詳細**: [`../research/adult-scope-2026-09-18.md`](../research/adult-scope-2026-09-18.md)。
ストアごとの扱いは `../stores/dlsite.md` §4 と `../stores/pokedora.md` §4。

## 10. 別名義は信頼できる情報に基づく場合のみ紐付ける

**決定**: 別名義の紐付けは、本人・事務所の公表情報、ストア自身が同一人物として扱っている事実、
出典のある公開情報のいずれかがある場合に限る。
声質・作風・活動時期からの推測、LLM による判断、運用者の心証は認めない。

**日付**: 2026-09-18 (ユーザー決定)

**根拠**: 間違えたときの被害 (実在の人物に、公表していない出演作を結び付ける) が大きい。
成人向けかどうかとは独立した原則として立てる。

**実測で分かったこと**: **DLsite からは別名義の根拠が得られない。**
`creaters` の id と name はスナップショット 2,275 件で完全な 1 対 1 だった。
ポケドラの `tag_id` も、492 作品の観測で 2 つ以上の表記を持つものが 0 件だった。

**帰結**: 当面、別名義の根拠は本人・事務所の公表情報に限られる。R18 を対象外にした以上 (§9)、
優先度は低い。`tag_id` は原則に合致する根拠ではあるので、将来の結合キーとして観測だけ続ける。

**詳細**: [`../stores/dlsite.md`](../stores/dlsite.md) §6、
[`../stores/pokedora.md`](../stores/pokedora.md) §6。

## 13. audiobook.jp は規約照会が前提

**決定**: audiobook.jp の実装には、運営元 (株式会社オトバンク) への事前照会を前提とする。
返信が来るまで着手しない。照会はユーザーが行う。

**日付**: 2026-09-18

**根拠**: 利用規約 第15条(15) が「当社の事前の許可なく、情報解析（生成AIに学習させることを
含むが、これに限らない）をする行為」を禁じている。本プロジェクトの取得がこれに当たるかは
条文から判断できない。「事前の許可なく」と明記されている以上、実装前に照会する。
robots.txt は `Disallow: /public/index.php/` のみで取得を禁じておらず、
**robots.txt と規約が食い違っているのではなく、規約のほうが厳しい**という状態。

**帰結**: 返信内容 (許可 / 条件付き / 不許可) で進め方が変わる。待つ間はポケドラを進める。
着手しないので `../stores/` に audiobook.jp のファイルは作らない。

**詳細**: 文面は

## 14. 取り込みにプロトコル版を持たせ、失敗を必ず記録する

**決定**: (1) スキーマとマイグレーションは同時に適用し、クロール中にスキーマを変えない。
(2) `IngestPayload` にプロトコル版を持たせ、不一致なら 409 を返してクローラーを即座に中断する。
(3) 取り込み失敗は最小のペイロード (`works: []` + `error`) を送り直して必ず `crawl_runs` に残す。
(4)「取得成功」と「保存成功」を分けて集計し、監視は `count(*) WHERE work_count > 0` の増加で見る。
**日付**: 2026-09-18 (**事故から得た教訓**)。規則は [`migrations.md`](../../.claude/rules/migrations.md)

**何が起きたか**: 500 人のクロール実行中に `AudioWork.adult: boolean` を `ageRating` の列挙に
変え、マイグレーションの適用だけ保留した。クローラーは起動時のコードのまま、サーバーだけが
ホットリロードで新スキーマに切り替わる**バージョンのねじれ**が起き、**81 人目以降 420 人ぶん、
4.5 時間の作品が保存されなかった**。ingest が HTTP 400 のときは `crawl_runs` に行すら作られず
**気付けなかった**。1,000 回の取り込みのうち記録が残ったのは作品 0 件の 524 件だけで、
作品があった 476 件は痕跡なしだった (事後の調査で判明した)。

**もう 1 つの教訓**: 当初は「81 人目以降が全滅」と誤認し、`work_count = 0` の 364 行を削除しよう
とした。実際はすべて正常なデータで、実装担当が止めた。**事故の調査中に出す指示ほど前提を検算する。**

**一般化**: 長時間動くプロセスと途中で更新されうるサーバーが対の構成では、**沈黙する失敗**が
最も高くつく。失敗は必ず記録し、かつ早期に全体を止める。

## 16. 人名の異体字を名寄せで畳む

**決定**: 情報源によって割れる漢字の字体 (ポケドラが `天﨑滉平`、AniList が `天崎滉平`) を畳む。
根拠を 4 段に分け、機械的に導けるもの (NFKC の正準分解、異体字セレクタの除去) と、
表で持つもの (互換漢字 1 組、常用漢字表の康熙字典体 17 組、表外の人名異体字 4 組) を区別する。
**日付**: 2026-09-19。**1 組ごとに出典をコメントで残す**。実装は `src/domain/normalize.ts`。

**根拠**: `﨑` と `崎` が同じ字であることは、**Unicode の互換関係と常用漢字表 (平成22年内閣告示
第2号) から機械的に判定できる事実**であり、根拠を示せる。
声質・作風・活動時期からの同一視 (§10 で禁止) とは性質が違う。

**入れなかったもの**: 嶋・嶌→島、冨→富、嵜→崎、舘→館、桧→檜、籔→藪。異体字ではあるが
**別の姓として使い分けられて**おり、実データで一致が 1 件も増えなかった。

**失敗の向きが安全**: 変換表が広すぎて別人が同じ鍵に落ちても、`resolveCredit` は**複数一致を
unmatched として返す**。誤マッチではなく取りこぼしで済む。回帰テストで固定した。

**検証**: 名寄せ索引 7,523 件で新規の衝突 0 組。未解決クレジット 2,039 件のうち 11 件が解決し
(天﨑滉平 6、日髙のり子 2 ほか)、再実行で 0 件になり冪等だった。

## 17. Audible の `sort=` を robots.txt 違反として取り下げ、ページングに置き換えた

**決定**: Audible の検索で `sort=` を使わない。検索 URL は `?searchNarrator={名前}` だけにし、
網羅は `&page=N` のページングで行う (上限 10 ページ)。**パラメータの順序を入れ替えて規則の
字面をすり抜けることはしない。** **日付**: 2026-09-19 (T25。**実装した同じ日のうちに取り下げた**)

**根拠**: `Disallow: /search?searchNarrator=*&sort=` は `sort` の**値を問わず**禁じており、
実装した並び順 6 種類はすべて禁止対象だった。一方 `page=` を禁じる行はどれも別のパラメータ
(`title=` / `keywords=` / `node=` / `sort=`) を必須にしていて、`searchNarrator` + `page` の形に
一致する行が無い。網羅率はむしろ上がった。斉藤壮馬 (総件数 164) で **83/164 → 164/164**。

**覆したもの**: 2 つある。

- **「並び順のはしごで網羅率を上げる」(T22)**。根拠にしていたのは「`sort` 単独なら HTTP 200 が
  返る」という**サーバーの応答**だった。応答は「技術的に取れるか」しか答えない
- **「robots が `page=` との組み合わせを禁じている」という読み違え**。使える手段を自分で潰し、
  埋め合わせに違反する手段を実装していた。**「禁止されている」と書くときも条文を引く**

**この失敗の扱い**: 同じ種類の失敗が 4 回続いたため、外部サイトの制約を [`../stores/`](../stores/)
に集約し、[`crawler.md`](../../.claude/rules/crawler.md) で確認を義務づけた (細部は `audible.md`)。

## 18. 外部サイトの制約を独立した文書にまとめる

2026-09-19。**同じ種類の失敗を 4 回繰り返したため**。

| 失敗 | 内容 |
|---|---|
| DLsite `per_page` | 「0 件になる」と記録したが実際は「無視される」 |
| DLsite `Crawl-delay` | robots が 10 秒を指定しているのに 2 秒で叩いていた |
| Audible `page=` | 「禁止」と読んだが、禁止は `node=` / `sort=` との組み合わせだけ |
| Audible `sort=` | robots が明確に禁じているのに 6 種類の並び順を実装した (同日に発覚、修正) |

そこから導いた「使ってよい URL」「使ってはいけない URL」を根拠付きで書く。
`.claude/rules/crawler.md` (`paths: crawler/**`) が、adapter を触ったときにこれを読むよう促す。

詳細は `docs/stores/README.md`。
