# 通知を Web Push で始める

Date: 2026-09-18
Status: 提案 / 未着手
Scope: 通知の実現手段の順序についての案。通知そのものの是非は `architecture.md` §9 で決定済み。

先行資料: `docs/design/architecture.md` §9、`docs/design/decisions.md` §5

推測には「（推測）」と明記する。

---

## 提供できる価値

**フォローした声優に新作が出たときに届く。しかもメールアドレスもアカウント登録も要らない。**

競合 2 社はどちらも通知を持たない (2026-09-18 実測)。OshiKiku にはお気に入り機能自体が無く、
KOE FOLIO の記録機能は端末ローカル。**通知は現時点で他社に無い価値**であり、
早く出せることに意味がある。

そして登録の手間が無いことは、それ自体が価値になる。
年に数回しか鳴らない通知のためにアカウントを作る人は少ない（推測）。

---

## 大まかにどういうことができるか

- ブラウザの通知許可だけで受け取れるようにする
- 現在の匿名フォロー (ブラウザ内に保存) のまま成立する
- メールでの通知は、必要になった時点で足す

---

## なぜ先に Web Push か

`architecture.md` §9 は OAuth による登録とメール送信基盤を前提にしている。これには:

- 外部のメール送信プロバイダの選定と契約（ユーザー作業）
- OAuth の実装と、フォロー状態をサーバーへ同期する経路

が要る。`decisions.md` §5 のとおり通知は「めったに鳴らない」ものなので、
その頻度に対して用意するものが重い。

Web Push なら、その手前で通知という価値を立てられる。

---

## 欠点

- **端末をまたげない。** PC で購読しても携帯には届かない
- **iOS の制約がある**（ホーム画面追加が要るなど。詳細は未確認）
- **購読が切れたときに復旧できない。** 宛先が端末に紐づくため、連絡手段が無くなる
- 長期的な宛先としてはメールのほうが確実

---

## 既存の決定との関係

`architecture.md` §9 を置き換える案ではなく、**順序の提案**。
Web Push を先に出し、メール通知は後から併存させる。

§11 で RSS は「一般ユーザーが使わない」として却下されているが、Web Push は検討されていない。
